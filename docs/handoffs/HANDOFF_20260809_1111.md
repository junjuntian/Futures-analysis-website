## 2. 分支拓扑(最关键,别搞乱)

两条分支,职责不同:

- **`phase/05-spread-analytics`**:代码源头 + 规范 workflow。当前 HEAD `49f3dcd`。所有业务代码、Dockerfile、`.github/workflows/*` 的规范版本都在这里。
- **`deploy/phase-5a-candidate`**:部署候选支。当前 HEAD `decdef0`。它 = `phase/05` + **仅两个 e2e 脚本的 delta**(`rust/tests/phase_4a_e2e.sh`、`rust/tests/phase_5a_e2e.sh`)。

铁律:部署工作流有"仅白名单差异"校验(`deploy-futures.yml` 约 106 行),要求 `git_sha`(=phase/05)与 `acceptance_sha`(=candidate)之间**只能差**这几个文件:`deploy-futures.yml`、`phase_4a_e2e.sh`、`phase_5a_e2e.sh`、`202608030003` 迁移。

- `ci.yml` **不在白名单**,所以它在两支上必须完全一致 → 任何 ci.yml 改动只放 `phase/05`,candidate 从 phase/05 继承,绝不在 candidate 单独改。
- 已用 `git diff --name-only phase/05 candidate` 核验当前只差两个 e2e 脚本,部署门会过。
- 更新 candidate 的正确方法:从新的 phase/05 tip 建分支 → 覆盖两个 e2e 脚本(acceptance 版本)→ 提交 → `push -f`。不要在旧 base 上叠加(会引入非白名单差异导致部署失败,本人踩过)。

## 6. 下次部署参数(本次会话执行中,若需重跑照此)

```
gh workflow run deploy-futures.yml --ref deploy/phase-5a-candidate \
  -f git_sha=<phase/05 tip,当前 49f3dcd 完整40位> \
  -f acceptance_sha=<candidate tip,当前 decdef0 完整40位> \
  -f api_digest=... worker_digest=... frontend_digest=... collector_digest=...  # 从 container-images run 日志取(cargo-chef 首次冷构建较慢)
  -f collection_date=<最近已完成交易日,勿用当天,新浪对最近交易日有发布延迟>
  -f provision_collector=false \
  -f run_live_collection=false   # 本候选与采集逻辑无关,跳过真采省~1h
```

部署前若在 16:30-22:30 采集窗口,可临时注释 `/etc/futures-platform/secrets`... 不,是 `/etc/cron.d/futures-collector`(备份在 `/root/futures-collector.cron.bak`),部署后恢复。或直接 `run_live_collection=false` 时其实不冲突,但 cron 采集与部署切换仍可能撞,稳妥起见部署期停 cron。
