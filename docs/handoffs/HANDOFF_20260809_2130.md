## 2. 当天查出的两个生产故障（都已修，**未部署**）

### 2.1 定时采集从装上以来一次都没成功过

`/var/log/futures-collector.log` 里只有 9 行错误、零成功：

```
error while interpolating services.api.image: required variable IMAGE_TAG is missing a value
```

根因：`docker-compose.production.yml` 把四个镜像写成 `${IMAGE_TAG:?...}`，**compose 会先逐个文件插值再合并**，所以哪怕紧接着的 `docker-compose.release.yml` 用 digest 覆盖了这四个镜像，这个 `:?` 也先把整条命令打死。部署任务里 `export IMAGE_TAG` 了所以从没碰到；cron 包装脚本没有。

**bug 在仓库文件 `deploy/collector/run-collector.sh` 里，重新 provision 修不好，必须改代码。** 修复 `d37c618`：从 `stable.env` 的 `previous_git_sha` 派生并 export（值是惰性的，真正生效的仍是 digest，它只是让插值能过）。

后果：`market_prices` 与 `trading_calendar_days` 都停在 **2026-08-05**，**2026-08-04 整天为空**。现存交易日基本都是当天恰好有部署、被部署里的 e2e 顺手采进去的。

### 2.2 交易日历只采了半个月，散户截止日就被算错

散户截止日 = 「日历里交割月前一个月的最后一个交易日」。日历只装采到的天数，所以**一个还在采的月份和一个采完的月份长得一模一样**，它最新那行直接冒充当月最后一个交易日。日历卡在 08-05，于是所有 2609 合约的截止日被算成 08-05（正确应为 08-31），自由价差图把 08-06、08-07 当「散户不可交易」剔掉，每个组合都少 2 个点，页面上没有任何提示。

修复 `6b79a66`：只有当日历已越过目标月（存在晚于该月末的交易日）才信它，否则走原有回退（对没采过的月份本来就是对的，且自带 nil calendar version 标记近似）。

**两个故障是串联的**：2.1 让日历停摆，2.2 把停摆放大成图上的数据缺失。修好 2.1 后 2.2 的症状会自行消失，但 2.2 的缺陷仍在——采集只要落后就会复发，所以两条都必须修。

## 3. 东方财富席位接入（`DEC-043`，本轮新增）

运营者 2026-08-09 授权。完整规格见 `docs/DECISIONS.md` 的 `DEC-043` 与 `docs/phases/PHASE_04_AKSHARE_COLLECTION.md` 第 3.x 节，这里只记要点与坑。

- **`1111` 文档里那个接口地址是错的**：`qhhqzl.eastmoney.com/marketFutuWeb/dragonAndTigerInfo/getLongAndShortPosition` 对任何参数组合都返回 `code:40000`。真实接口是 `datacenter-web.eastmoney.com/api/data/v1/get`，报表 `RPT_FUTU_DAILYPOSITION`，`filter=(TRADE_DATE='YYYY-MM-DD')(TYPE="0")`，`SECURITY_CODE` **必须大写**（小写返回空），`pageSize` 被服务端硬性截到 500。
- **不经 AKShare**：锁定版 1.18.81 没有任何东财期货席位函数。该源由采集器自有 HTTP 客户端直连，但仍跑在 `official_requests_only` 的域名白名单 + DNS 围栏里。`connector_code` 独立为 `eastmoney_seats_v1`（迁移 `202608090002` 放行），不复用 `akshare_v1`，免得谎报取数方式。

## 6.5 部署后核实查出的两处「文档说的和机器上的不一样」

两处都是同一类错误:**据一条不够有力的命令下了结论,没有直接看东西在不在**。

### 6.5.1 `run-backfill.sh` 从来没被部署过

`deploy-futures.yml` 只打包并安装 `run-collector.sh`、`futures-collector.cron`、
`futures-collector.logrotate` 三个文件。**回填驱动不在发布包里**,生产上那份
`/usr/local/sbin/run-futures-backfill` 时间戳停在 **2026-08-05 05:29**,是当初手工装的,
此后仓库里对它的任何改动都只停在仓库。

所以 `f7374e4` 提交信息里那句「回填驱动现在默认 DCE/SHFE/CZCE」**对仓库成立、对生产不成立**。
已修:把它与 collector 包装脚本并列打包与安装,并在 `dce_fallback_is_the_only_aggregator...`
测试里加了断言——**仓库拥有的每个运维脚本,必须同时出现在打包与安装两处**,
少一处就红。

### 6.5.2 `futures-backfill-phase4b1.service` 这个 systemd 单元不存在

`1111` 文档写它「inactive,恢复=`systemctl enable --now`」。实证:
`/etc/systemd/system`、`/lib/systemd/system`、`/run/systemd/system` 下都没有该文件,
`systemctl status` 回答 `could not be found`。

**陷阱**:`systemctl is-active <不存在的单元>` 会回答 **`inactive`**(退出码 4),
和「装了但停着」的回答一模一样。当初就是据此误判的。

后果:生产上 `/etc/futures-platform/BACKFILL-PAUSED-BY-OPERATOR.txt` 里写的
`resume: systemctl enable --now futures-backfill-phase4b1` **执行了什么也不会发生**。
回填实际是手工跑脚本。该标记文件是生产状态,**未改动**,等运营者决定是要改文案还是
干脆补一个真的 systemd 单元。

**通用教训**:判断一个单元/文件/脚本在不在,`ls` 它,别问一个对缺失和停用给同样答案的命令。
