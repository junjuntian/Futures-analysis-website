## 一、生产库操作

- **用旧检出的脚本重算,把 45 天新列刷成 NULL**(2026-08-18)。`/opt/futures-platform`
  是旧 git 检出,只有 `load/` 被采集用作 CSV 落盘,**代码一律不从那取**。手动重算
  唯一正确来源:`. /var/lib/futures-platform/deployments/stable.env` 后用
  `$previous_release_dir/deploy/collector/…`。
- **grep 剥 `commit;` 做"跑一遍再回滚",转义失效把 DDL 真落进生产**(2026-08-17)。
  要么复制一份改好的脚本,要么不在生产库上试。迁移因此全部要求幂等
  (`add column if not exists`、`drop constraint if exists` + `add`)。
- **只读验证截掉写操作,约束从没被检验过**:`move >= 0` 写错,部署后全量重算才被
  check 拦下(202608170003)。只读验证必须另配值域检查。
- **sane 护栏拦住的是脏数据,我却放宽了护栏**(2026-08-18,**已勘误**):回填撞
  `prev_years_position = −12.26`,我判定「真实观测、百分位区间被撑爆」并放宽护栏
  到 ±100(迁移 202608180002);当天晚些查证发现那是收盘价 0 造成的假价差
  (见本文四·收盘价 0 与 `DEC-073`)。**护栏本来是对的。**
  insert 单语句原子回滚,现网全程无损——但**约束报错时的第一动作是去查被拦那行的
  原始数据,不是放宽约束**。修完根因重算后实际值域只有 −2.85~5.01,护栏已由
  202608180004 收回 ±10(**先重算再收紧,顺序反了会被 check 拒绝**)。
- **RLS 下无上下文查询返回 0 行假象**:业务表全 FORCE RLS,连 owner 也被过滤。
  核数要 `set local role` + `set_config('app.current_workspace_id', …)`,或用管理员
  绕 RLS。runtime 角色 nologin,psql 冒烟用 `set local role futures_runtime`。
  库名是 `futures_platform` 不是 `futures`。

## 二、发布链

- **dispatch 的 SHA 凭记忆打错被门禁拦下**:必须从 `git log` 复制完整 40 位;
  digest 不要从构建日志 grep(secret 打码会污染),用 preflight 脚本取。
- **建镜像到部署完成之间推了提交**(包括纯文档提交)→ `acceptance_sha` 守卫拒绝,
  镜像整套重建。文档等部署完再推。
- **同分支并发**:另一会话在你 push 后又 push,workflow_dispatch 取分支 HEAD 构建,
  传旧 SHA 就出身不匹配。部署前 fetch 核对 HEAD。
- **新迁移忘进 `deploy-futures.yml` 显式清单**:代码上线 schema 没到,全站 500。
  加迁移与改清单必须同一笔提交。
- **engine/ 打包也是白名单式 install,新增 .py 模块必须同笔提交列进
  deploy-futures.yml**(2026-08-24,DEC-133 部署前自查抓住):`campaign.py`
  不列,线上 `import campaign` 直接 ImportError,而 run_one 捕获异常
  「保留上一版」——页面照常显示旧信号,**不会报错**。三处都要:发布包
  install、主机回滚备份清单、ENGINE_CHANGED 判定。
- **自动化发布链脚本:每一环的产物 id 必须来自那一环自己的输出,失败必须
  让后续环止步**(2026-08-24,DEC-138 首轮"部署成功"是假的):
  `gh workflow run` 撞上 GitHub API 瞬断(EOF)没创建构建,preflight 正确
  红了没 dispatch,但链条用 `&&`+管道把 preflight 的退出码吞了,又用
  `gh run list --limit 1` 抓"最新部署 run"——抓到的是**上一轮**的 success,
  于是整条链报「deploy=0 success」而生产一个字节没变。发现靠的是核对
  payload 新字段全空。规矩:①dispatch 后的 run id 要么从 dispatch 输出
  解析,要么校验 createdAt 晚于 dispatch 时刻;②preflight 是否放行要
  grep 它的放行文案做显式分支;③链条报成功后,仍要用**产物本身**
  (payload 字段/stable.env SHA)复核一次——这次正是这一步救的。
- **改申报/契约只改了消费方**:生产方代码没进提交,值恒空回退。改任何"值"提交前
  全仓库 grep 旧值;生产方消费方同一笔提交。
- **CI clippy 按 `-D warnings` 跑**:本地裸 `cargo clippy` 数 error 是 0 也可能挂
  CI(如 doc_lazy_continuation)。本地第 0 步就带 `-- -D warnings`。
- **e2e 脚本搬代码遗留未定义变量/不存在文件,第一次真实执行才炸**。改采集/验收
  脚本后 `bash -n` + shellcheck,并检查引用的夹具文件存在。
- **部署偶发 `DEPLOY_FAIL ghcr_login_failed`(token_http=403)**:2026-08-18 出过一次,
  同一套 digest、同一条链、四十分钟前刚成功过,原样重发 dispatch 即通过。这是
  GHCR 侧的瞬时拒绝,不是权限配置问题——**先原样重试一次再排查**,不要一上来就
  去动 workflow 的 permissions 或换 token。生产在这种失败下不受影响:镜像还没拉,
  切换没发生,`stable.env` 仍指向旧发布。

### 部署验收 phase5a「jm 09-01 cache hit」在北京时间零点附近会假失败(2026-08-23)

现象:deploy-futures 在 16:05 UTC(北京 00:05)验收失败 `PHASE5A_E2E_FAIL http_label=jm 09-01 cache hit expected=200 actual=503`,
证据 live-combo-hit.json 是 `spread_provider_unavailable retry_after 58s` —— 第二次同样的查询没命中缓存、打到上游被限流。
第一次查询在零点前、第二次在零点后,缓存键跟着日期变了。自动回滚 ROLLBACK_PASS,生产停在上一版,无损。
**处置:避开北京 23:55~00:10 部署;撞上了直接重新 dispatch 即可(本次重跑即过)。** 与业务改动无关,别去改代码。


### 部署窗口内的「研究提交」也是提交(2026-08-25,DEC-145 首次部署被拦)

镜像建在 5eb6bba,部署跑到一半时往分支推了一个"纯研究附录"提交(23556f3),
deploy-futures 的版本一致性校验(`test "$acceptance_sha" = "$GITHUB_SHA"`)直接拒绝,
部署步骤全部跳过(生产无影响,门起了作用)。教训:**零提交铁律不分提交内容**——
research/docs 的提交一样会动 HEAD,一样触发拒绝;部署链在后台跑的时候,任何
`git push` 都要等它落地。返工成本 = 重建镜像 + 重跑整条链(约 20 分钟)。
连带认知:失败 run 里 Step 10(registry 凭据校验)的 SSH 报错是**果不是因**
(Step 6 装密钥被跳过了),看失败先看**第一个** failure 的步骤,别被最后一个骗走。

### `git push | tail -1` 又吞了一次推送失败(2026-08-26,DEC-149 二改)

远端有部署流水线的自动 LATEST 提交,push 被拒(非快进),`| tail -1` 让链条
当没事继续——带着**没推上去的代码**跑完 CI/镜像,到 preflight 才被拦。
与「发布链假成功」是同一类病:**发布链一律 `set -o pipefail` 开头**,任何
`cmd | tail/grep` 后面接 `&&` 都默认有这个坑。写进链条模板,不靠记性。


## 三、生产服务器(qh)运维

- **长活儿一律 `nohup` 后台跑,别指望 ssh 会等你**(2026-08-31)。`ssh_execute`
  的超时到点会掐断连接,连着把远端的 psql 一起杀掉:装 26 万行那次跑到一半被
  断,整个事务回滚,`COPY` 白做。**这次是 `ON_ERROR_STOP` + 单事务救了场
  (库里零残留)**,换成分段提交的脚本就是半截数据。凡是预计超过一分钟的
  采集/解析/装载,`nohup … &` + 轮询日志,别放在前台等。
- **cron 的 `CRON_TZ=Asia/Shanghai` 在这台机器上不生效**(三例):写北京时间会按
  UTC 解释,任务在凌晨跑或从未跑过。一律写 UTC。
- **"脚本里写了"≠"被执行过"**:采集器非零退出 + `set -e` 曾让日更投影**从未**
  自动成功;`docker images | grep | head` 在 pipefail 下 SIGPIPE 141 杀全脚本
  (禁用 head 截断长流,用 awk 首匹配)。验证管线要验每一步的产物时间戳。
- **服务器上的文件副本会漂**:`/opt/futures-platform/parsers.py` 曾是仓库旧副本,
  郑商所世纪判错每天发生。engine/ 现已随发布包自动装到
  `/opt/futures-platform/smart-money/`(2026-08-18 实证 md5 一致),
  "引擎要手动 install" 的旧说法作废。
- **别在采集窗口里部署,否则那一轮整轮跳过**(2026-08-20 实抓,运营者当场发现
  「生猪没有最新的蜡烛图」):部署与采集抢同一把 `/run/lock/futures-collector.lock`
  (迁移要 AccessExclusiveLock,与正在写 `seat_history` 的采集撞上是死锁),
  **部署优先、采集整轮跳过**——这是有意设计,下一轮会补。代价是中间那几小时页面
  上是缺的:上期所/郑商所有官方源不受影响,**大商所(JD/JM/LH)只有新浪一条路**,
  当天就少一半合约,最新一根蜡烛画不出来。那天我连部署三次,其中一次正压在
  09:30 UTC 上,四小时后运营者看生猪就撞上了。
  采集轮是 **08:00 / 09:30 / 13:30 UTC**(北京 16:00 / 17:30 / 21:30);
  `ops/preflight-deploy.sh` 现在会在 ±20 分钟内**黄字提醒但不拦**——急着修线上
  该部署还得部署,只是部署完记得手动补跑一次 `/usr/local/sbin/run-futures-collector`。
  **排查这类现象先看 `/var/log/futures-collector.log` 有没有 `COLLECTION_SKIPPED`**
  ——那行字就是为了让漏掉的一轮看得见才加的,别一上来就怀疑画图或数据源。
- **产出给别人读的文件,模式要写死,不能靠继承 umask**(2026-08-20,403 事故):
  `run-smart-money.sh` 用 `cp` 落盘,模式随调用者的 umask 走——cron 是 022 出 644,
  部署脚本是 077 出 600,容器内非 root 的 nginx 读不到,机构资金全站 403。
  同一个脚本被 cron/部署/人手动各调一遍,umask 各不相同。一律 `install -m 644`,
  并在脚本收尾扫一遍产出目录的权限,不对就吼并纠正。**写完不验,下次 umask
  再变又是一次静默的 403。**
- **ssh_execute 长 sleep 必超时**:超时不杀远程进程,别重发命令(会双跑)。
  长任务 nohup + 日志文件,60 秒短轮询;等待用 `grep -q EXIT= 日志` 判完成。
- **ssh_execute 传大文件禁用 heredoc**:单行大 base64 经 heredoc 会中段变形
  (同尺寸字节替换,极难察觉)。用 `printf '%s' '<b64>' | base64 -d > 文件`,
  落地后 **md5 与本地对拍**,不一致不许执行。

## 四、数据口径

- **「要不要这个品种」与「从哪个源要」是两件事,混成一件会撞键**(2026-08-31)。
  加 SC 只是往 `parsers.WANT` 里塞了一行,但上期所的 `dailydata` 文件里本来就带着
  上期能源的原油——`sc_f`(主合约)与 `sc_tas`(结算价交易合约)去掉后缀是同一个
  `SC`,同代码同交割月,于是两行撞同一个身份键,`ON CONFLICT DO UPDATE command
  cannot affect row a second time`,**整批 upsert 中止**。代价不是少一个品种:
  price 与 seat 走同一个事务,当天 **SHFE 与 CZCE 的行情和席位一起没入库**,
  运营者在「数据到齐了吗」卡片上看到两个交易所停在上一交易日。
  正确做法:源解析器只收**属于这个交易所**的品种(`wanted_from(variety, "SHFE")`,
  按 `EXCHANGE_BY_VARIETY` 判),并显式跳过 `_tas`。
  **加品种的白名单清单要连"这个品种会不会从别的源顺带流进来"一起过一遍**——
  SC 的行情本来就由 `ine-daily.py` 单采,从 SHFE 再收一份纯属多余,而且 exchange
  会被标成 SHFE,与 INE 那份互不去重(正是 `EXCHANGE_BY_VARIETY` 注释警告的那种错)。
  另一课:**upsert 撞键是整批中止,不是跳过那一行**——一个新品种能连坐两个交易所。
- **榜上无名 ≠ 清仓**:龙虎榜是前 20 截断,小席位掉榜常在门槛边缘。回榜日
  `回榜量 − 当日增减 = 前日全量仓` 可反推;反推行 `reboard_inferred` 不进任何
  汇总与规则,只作展示(吸收律:任何一腿增减缺失,整个反推作废)。
- **同一个文件里,一条纪律只落实了一半**(2026-08-21,DEC-111)。
  `main_series` 开头写着「跨合约相除会凭空多出几个百分点,而且不报错」,
  `ret` / `ret_open` 都照办了,**唯独 `past` 是 `settle.pct_change(20)`** ——
  纯碱换月那天 990 → 1031(+4.1% 全是合约价差),于是「近 20 日在涨」把一个
  真做多信号挡掉了。实际近 20 日是 −3.3%。
  判据符号被改写的天数:鸡蛋 12.2%、生猪 10.4%、纯碱 8.6%、玻璃 7.5%、焦煤 5.6%。
  **写下纪律不等于执行了纪律**:查这类问题要按「这条纪律涉及的每个量」逐个数,
  不能因为文件顶上有那段注释就认为都办到了。
- **开一个此前没人走过的分支,先看那个分支读的量对不对**(2026-08-21,DEC-111)。
  `past` 写错很久,但纯碱一直 `long_needs_dip: False` 不读它;
  DEC-110 把它开成 True,当天就吃掉一个真信号。翻开关时我只比了两档回测数字,
  没回头看判据本身。**回测数字对比看不见这类错误** —— 两档都跑在同一个坏量上。
- **空头的「加仓/减仓」要按绝对值判,不能用净持仓的代数差**(2026-08-18):
  净空 −10,621 → −7,143 的代数差是 +3,478,看着像加仓,实际是空单减了 3,478 手。
  加减说的是仓位变大还是变小,与方向无关。
- **缺席 = 未知 ≠ 零**:掉榜日持仓一律 NULL,补零会一路错到成本引擎。
  增减量渲染三态:undefined=无行计 0 / null=有行但源没给(污染整个求和)/ number。
- **多源重复行灌水**:同一天同一合约在多个源下各一行。数"共同交易日"必须
  `distinct trade_date`(曾把 58 灌成 67,导致误判门槛);席位求和必须先按
  `member_key`(剥括号+别名)+ 来源优先级去重——东财写「一德期货(代客)」、
  三禾写「一德期货」,不归一化就把一家算成两家(2026-08-18,只有 DCE 双源
  并存的日子中招)。
- **临时分析 SQL 必须走与生产同一套归一化**,否则会把自己的写法问题误判成
  生产缺陷上报(「(代客)」事件:先报"影响面很大",查证后 Rust 展示路径因
  member_key 本就免疫,页面一直正确)。**上报缺陷前先查读时去重是否已覆盖。**
- **收盘价 0 不是价格,是「当天无成交」**(2026-08-18,9,795 行):郑商所如实写 0
  且结算价有效。只挡 NULL 不挡 0,价差就算成 `0 − 对手价`,假极值**永久钉死
  区间下界**(AP2603−AP2605 下界 −10753 vs 真实 −1313),造出假报警假拐头。
  取价一律 `coalesce(nullif(close_price,0), settlement_price)`。
- **PG boolean 经 CSV 是 't'/'f'**:pandas 按 str 读入后 `astype(bool)` 把 'f'
  判 True。必须 `.isin(['t','true','1'])`。
- **PHP/JSON 浮点**:float 整值印 2 不印 2.0;DATETIME 列 sqlx 必须 CAST。
  (这两条来自 shejimao 面板,同机型教训。)
- **名字长得像不等于是同一家,先查「有没有同日同榜并存」**(2026-08-19,格林)。
  合并归一之前必须问一句:这两个名字在同一天、同一合约、同一榜单上一起出现过吗?
  出现过就是**两家**——一张榜上同一家不可能占两个名次。「格林期货」与「大华期货」
  并存 266 次(2008-04-29~2013-09-17),是 2013 年吸收合并前的两家;而「格林期货」
  与「格林大华」只在交接当天 2014-03-27 并存、且持仓**逐笔相同**,那才是更名。
  判据是数据不是字面:并存次数 + 交接日数值是否逐笔相等 + 品种/交易所是否重叠。
- **「三个名字重复,删掉两个」——先查它们覆盖的范围是不是互补的**(2026-08-19)。
  运营者报「格林有三个名字,数据应该是一样的」,实态是三个各管一段:「格林大华」
  只在上期所大商所、「格林大华期货」只在郑商所、「格林期货」是 2014 年前的旧名,
  **品种零重叠**。照「重复」处理会丢掉郑商所三个品种的全部持仓与 2014 年前的历史。
  同一个现象(下拉里冒出好几个相似的名字)可以是重复,也可以是互补,**先看它们各自
  覆盖什么,再决定是删是并**。
- **源命名/更名**:乾坤→高盛(2026-05-26)等别名只在 `MEMBER_ALIASES`
  (spread_analytics.rs)一处维护,SQL 键与 Rust 归一都从它生成;engine 的
  alias 表保持同集。归一化只进展示/去重键,**过滤一律走原始列**(RLS 教训:
  regexp 进 WHERE 退化全表扫,会员下拉整个空掉)。
- **同一个缺陷有两条取数路径时,只修一条不会有人告诉你**(2026-09-03,DEC-187)。
  「残缺的高优先级行顶掉旁边的完整行」DEC-081 在 **SQL 侧**修过了(完整性过滤提到
  `distinct on` 之前),**引擎的 `clean_price` 一直没修**,于是大商所三天行情在
  页面上有、在引擎里没有,`main_series` 的 `dropna(subset=["open_interest"])`
  把整天丢掉,那三天没有信号且**不报错**。这是「修复是绑在函数上的,不是绑在功能上的」
  的又一例,而且当时的 DEC 条目里已经写清了根因 —— **修完要问一句:同样的取数
  还有谁在做**(这里是 SQL / 引擎 / research 三份)。
- **「这个品种没有官方源」会把一个通用缺陷变成单品种事故**(同上)。同一批 447 行
  残缺数据,郑商所上期所有官方源(优先级 0)压着,毫发无损;大商所只有新浪(3),
  被 akshare(1)压住就出事。**排查「只有某个交易所出问题」时,先看它的源优先级
  链上有没有兜底**,而不是先怀疑那个交易所的采集脚本。
- **完整性判据要定在「缺了会出什么后果」上,不是「缺了多少格」**(同上)。
  这次只拿 `open_interest` 当判据:缺持仓量会让**整个交易日消失**,缺开盘价只是
  那一格取不到值(无成交日本来就该缺,上期所 10,094 行如此)。若图省事按「四价
  全齐才算完整」,就会让低优先级源顶掉本来正常的官方行。

## 五、批量编辑与脚本工具

- **python 批量编辑:断言中途失败,前面的编辑已落盘、后面的没有**,然后照常
  commit(60a0d29 漏了迁移清单)。断言全部前置,或拆小笔逐个验证。
- **`s[:i] + helper + s[i:]` 插入时 helper 末尾带锚点文本 → 锚点重复**,产生
  unclosed delimiter。插入内容不要以锚点结尾。
- **锚点上下文不足,替换塞错同形代码处**(inferred 塞进错误的 mapper,编译器
  拦下)。锚点必须含足够独特上下文。
- **Bash heredoc 里的反斜杠会被二次转义**,Python 字符串尾随反斜杠直接
  SyntaxError 且整个脚本零编辑落盘。需要反斜杠用 `chr(92)`。
- **`\copy` 不做变量插值**:`\copy t from :'csv_path'` 会把路径当成空串,报
  `:: No such file or directory`。装载脚本一律写固定路径,与 run-collector.sh 里
  `docker cp` 的目标一一对应。(2026-08-18 重踩过一次——教训当时只写在
  load-seats-direct.sql 的注释里,**代码注释挡不住没读那个文件的人,所以提到本文**。)
  **2026-08-31 第三次踩**:改 `load_sanhe_seats.sql` 时主动把固定路径「改进」成
  参数,理由是「写死的路径会让下一个人灌错文件」——理由本身没错,错在**没先查
  本文就动装载脚本**。`\copy` 想要参数只有服务端 `COPY` 一条路,那要
  `pg_read_server_files` 权限,不值得。**动任何装载 .sql 之前,先读本节。**
- **批量替换失败之后,要重新核对每一处,不能凭记忆判断哪些成了**(2026-08-19)。
  一个 python 脚本里替换两处,第二处断言失败 → 整个脚本没落盘 → 我却以为
  「第一处成功了」,只用 Edit 补了第二处,于是留下「引擎要跑 LH,FG,SA 而导出只有 LH」
  的半吊子状态:**没有 CSV 引擎照样跑不出来,而且不报错**。
  PITFALLS 里原有一条说的是「前面已落盘、后面没有」,这次是另一种形态——
  **全部没落盘,但我按「前面成功了」去补**。失败后一律重新 grep 核对。
- **文件里的反斜杠续行可能已被展成单行,多行锚点会匹配落空**(2026-08-19)。
  shell 脚本里 `docker run --rm \` 那种续行,经过前几轮 heredoc 写入后在文件里
  已经是一整行。拿多行带 `\` 的字符串去匹配必然失败——而失败的表现只是
  「assert 报错」,容易被当成小问题跳过。**改 shell 脚本前先 `cat -A` 看真实形态。**
- **PowerShell 5.1 按 GBK 读 UTF-8**:改中文文档禁用 Get-Content/Set-Content,
  用 Edit 工具或 Python;改完查乱码字符数。

## 六、回测与统计方法

- **接别人的列,先看量纲再用**(2026-08-22,成本进场实验):
  `unload_series` 的 `pct` 是 **0~1 小数**,我当百分数用,阈值写 30/50,
  于是「机构没大规模减仓」这个条件**从未生效**,第一轮跑的其实是没有它的版本 ——
  而且不报错,结果表看着完全正常(两列阈值结果相同是唯一破绽)。
  一行 `describe()` 就能避免。同场第二个坑:**对照组的品种开关要跟基线一致**
  (焦煤生猪基线只做空,候选却双向跑,对比无效),修正后结论翻了一半。


- **单品种回测出的参数是过拟合**:「回撤 150 点」实为鸡蛋 08-02 区间的 20%,
  换品种无意义(运营者抓的)。通用化=无量纲化;门槛不做旋钮;结论要求
  「相邻档同向」而不是挑峰值。
- **扫描挑出的最优参数当天采纳、次日被回测否决**(DEC-055「区间下 70%」)。
  参数采纳前先做逐年留一的样本外检验;LH/FG 相邻档正负翻转=噪音,不挑。
- **凭印象写数据结论**:「FG-SA 一次穿线」写进文档后被数据证伪(实际两次)。
  叙事入档前先跑一遍数。
- **修了生产的数据口径,必须回头重跑所有旧回测**(2026-08-18,DEC-075):
  回测导出与生产 SQL 用同一个取价条件是对的(同源才一致),但**同一个缺陷会同时
  污染两边,自己验证不了自己**。收盘价 0 修掉后重测,AP 的深档优势从 14.7pt 缩到
  5.1pt、逐年一致性 8/8→5/8,样本外挑参收益直接归零——原结论被推翻,AP 退回默认档。
- **单边行情里,「谁赚得多」测的是方向暴露不是本事**(2026-08-19,生猪立项)。
  生猪三年单边熊市,一直挂空单就赚钱,累计盈亏榜前八全是净空席位。把「恒定仓位
  能赚到的钱」扣掉才看得见择时:运营者点名的永安期货 9.99 亿里只有 0.92 亿是择时
  (91% 是方向暴露),而平均只挂 227 手的东证期货 6.42 亿里有 5.40 亿。
  **验证方式很简单**:把这家的净持仓换成它自己的均值(仓位大小方向都不变)再算一遍,
  差额才是本事。同一段样本外实测:按 alpha 选 t=5.22、按总盈亏选 t=3.57、
  按仓位规模选 **t=0.11**。挑人之前先问「这个排名扣掉 beta 还剩什么」。
- **同一套方法换个品种可能整个反过来**(2026-08-19)。金银是「逐家席位算权重 ×
  多席位共振」,照搬到生猪会失败——生猪单家事件整体胜率只有 50%,而**八家合计的
  流向** t=5.4~7.5。品种的市场结构不同(生猪是产业套保 vs 散户,金银是投机资金),
  信号该聚合到哪一层就不同。**移植策略时先验证信号形态,不要只调参数。**
- **跨月合约的持仓变化,拆到合约层面会被移仓撕成相反的两半**(2026-08-19)。
  生猪逐合约信号 IC_t 只有 0.58,品种合计 t=5.22。查实:**84.6% 的交易日里同日
  不同合约的信号方向相反**,`|合计净变化|/Σ|各合约变化|` 中位数仅 0.62。机构看空的
  是品种,执行时分散在几个合约上;从近月移到远月,单看近月是「减空」远月是「加空」,
  方向一步没变。**「合约价差大」影响的是计价(必须逐合约),不是方向信号(该用品种
  合计)——两件事分开想。**
- **做空的复利收益不是买入持有取反**(2026-08-19,差点把基准写错)。价格跌 52.9%,
  恒定满仓做空的复利收益是 **+99.2%** 不是 +52.9%。用错基准会把「跑赢躺着不动」
  说成两倍于实际的优势。算基准就老老实实逐日累乘 `(1 − ret)`。
- **「跟随机构方向」要分清「减仓」和「转向」**(2026-08-19,生猪做多支路)。
  生猪信号 z>0 只表示机构**在减空**,不表示**转多**——15 笔做多进场当日,机构合计
  净持仓全部仍是负的(−28,284 ~ −974 手)。把「不那么看空了」当成「看多了」跟进去,
  三年逐笔累计 −1.5%、均值 −0.02%,纯属抛硬币。**先问信号的绝对水平在哪一侧,
  再看它的变化方向。**
- **一个事件里的 14 个交易日不是 14 个样本**(2026-08-19)。查「机构真转多之后
  会不会涨」,样本里净持仓转正共 14 天——但它们全挤在 2025-07 一个窗口里,实质
  只有**一个事件**。这种样本能得出的结论只有「没有证据支持」,不能是「证明了会跌」。
  报数时要把窗口分布写出来,只报 N=14 是在夸大证据强度。
- **同一个统计换个筛选口径可能整个翻掉**(2026-08-19)。DEC-083 写「机构一天都没
  转成净多、穿越零轴 0 次」——那是按**总盈亏**选的八家;换成按 **alpha** 选的五家,
  就有 14 天净多。**结论要连着「用哪组数据算的」一起写**,否则下一轮换了口径,
  旧结论会被当成事实继续引用。
- **全样本显著不等于稳定有效,要逐年看符号**(2026-08-19,玻璃)。玻璃合计流向全样本
  t=+2.96 看着能用,拆到逐年是 **7 年正、7 年负**——那个显著性是被 2019~2022 一段
  单独撑起来的。生猪同样的检验是 4 年全正。**报一个因子之前,先把逐年符号列出来数
  一遍**:符号一半一半的因子,再高的全样本 t 也是拼出来的。
- **别人质疑是不是方法没用对时,要把替代解释真的测掉再回答**(2026-08-19)。
  运营者提出玻璃跟着地产走、有牛熊,怀疑是市况没分对。这个替代解释很合理,不能靠
  嘴否掉——按 MA120、MA250、过去 60 日涨跌三种分法各测一遍(全部同号、不反向),
  结论才站得住。**测一次的成本,远低于把一个错误结论写进决策记录。**
- **自算收益的脚本,逐笔连乘与日收益累乘必须先对账**(2026-08-19,共振回测)。
  日收益序列用 `daily.loc[进场:出场] = seg*side` 这种**区间赋值**写,会把进场当日
  计入(实际 T+1 才有仓),而且前一笔的出场日与后一笔的进场日重合时相邻区间互相覆盖。
  症状:逐笔连乘 +1183% 而日收益累乘 +5010%,**差 3,827 个点**;累计收益(逐笔)
  本来是对的,错的是**回撤与夏普**——夏普一度虚报到 3.14。正确写法是先铺一条仓位
  序列(去掉进场日)再乘收益。**两条路的累计对不上就是有 bug,这是最便宜的自检。**
- **敏感性分析用了全局常量而不是传入参数,整节静默失效**(2026-08-19)。
  成本敏感性四档跑出**完全相同**的数字——因为 `stats()` 里写的是全局 `COST`,
  传进去的 `cost` 根本没用上。这种 bug 最阴:表格排得整整齐齐,数字全是假的。
  **扫参数时先看一眼各档结果是不是真的在变**,一模一样就是没接上。
- **「是散户」不等于「该进信号名单」**(2026-08-19)。中信建投确是散户(早期就亏、
  全品种净多、无前视也选得出),但加进名单后生猪从 5.96 掉到 5.03——它在生猪上
  只有 171 手,与被剔掉的中衍期货(FG 407 手、SA 58 手)是同一个毛病。
  **名单要的不是「把所有符合定义的都收进来」,而是一组在同一批品种上同步犯错的人。**
  实测四家不如三家,减一家也变差——**规模有甜点,不是越全越好**。
- **对比两个策略时,每一路必须各用各的信号进出场**(2026-08-19,生猪)。
  写对比脚本时把「反向出场」的判断统一写成了某一路的信号,连测另一路时也在用它,
  于是「只用现有引擎」那一行测出来的根本不是现有引擎,是个混合体。
  结果:现有信号被算成 +39.8%/夏普 1.73,真实是 **+79.7%/2.39**;据此得出的
  "新信号碾压旧信号"结论完全错误,还连累我做了一次基于错数的自我批评。
  **防呆办法:对比脚本第一件事是复刻出已上线那一路,与生产页面的数字对拍**,
  对上了后面的比较才算数——这次正是靠运营者对照页面发现对不上才揪出来的。
- **样本小的时候,先算差异的 t 再谈"谁更好"**(2026-08-19)。修正口径后三个信号
  是 +79.7% / +91.4% / +88.4%,看着差十来个点,但单笔均值差的 **t 只有 0.22~0.49**
  ——21 笔样本上根本分不出高下。**十几个点的累计差在几十笔样本上是噪音的正常幅度**,
  不做显著性检验就下"更优"的结论,等于拿噪音改规则。
- **同一套规则换个品种必须重验,不能照抄**(2026-08-19,玻璃纯碱上线)。
  生猪关掉做多支路(它样本里只有单边熊市,多头逐笔累计 −1.5%),照搬到玻璃就错:
  玻璃跨 13 年完整周期,双向夏普 1.63 vs 只做空 1.04。还有一条更隐蔽——
  `long_needs_dip` 这个生猪时代的遗留条件,带着它去跑玻璃**收益差 3.5 倍**
  (206 笔 +4264% → 157 笔 +1225%)。**每个品种的每个开关都要单独测一遍**,
  「上一个品种是这么设的」不是理由。
- **特征在标签事件点上分得开,不等于当成逐日策略不误伤**(2026-08-24,DEC-133
  研究期)。震仓 vs 认错的判别特征(对手浮盈/对手增仓)在 50 个卸仓事件点上
  两类中位数差异清晰,做成逐日出场规则却全面跑输——判据是在事件点上校准的,
  策略每天都在扫,平常日的假阳性率决定成败(高点日 55 个对平常日 1107 个,
  基率悬殊:信号日里只有约 10% 是真高点)。**把分类器变成策略前,先算它在
  全部扫描日上的触发频率,再算基率折扣。**
- **回放口径 ≠ 实盘记录**:历史 ⚡ 是"当时按今天规则会怎么标",不是当时真实
  报过的信号;统计盘后算,执行等于次日。
- **环形日历轴上「起点参差」伪装成「终点越界」**:叠年图先查各年窗口起止对齐。
- **写端点对拍要比落库字节**,响应一致不代表存的一样(充值码写库回空 body 案例,
  shejimao 侧教训,通用)。

## 七、判断与流程

- **缓存失效该由「数据变了」驱动,不是由时间驱动**(2026-08-18,运营者纠正
  我的第一版方案):报告表十几秒的重算,我先做成「TTL 延长 + 定时重算」,
  两头都错——空闲时段反复重算一模一样的东西,到点失效又让人再撞一次。
  正解是拿数据版本(相关表的 `max(updated_at)`)当缓存键,没变就永远命中。
  **贵的计算前面要问的是「它依赖的东西变了没有」,不是「过了多久」。**

- **"影响面很大"的结论要先自查验证路径**(见四·「(代客)」事件)。
- **约束拦住的值,先判断它是真实还是脏数据,再决定放宽还是修数据**
  (2026-08-18 反面案例):回填撞 sane 护栏,我查到历史低点 −8020 就判定
  「真实观测,百分位区间被撑爆」并放宽了护栏;实际那天收盘价是 0,是脏数据,
  **护栏本来是对的**。看到异常值先查它的原始行(是不是 0/NULL/单位错),
  查完再动守卫——放宽守卫是最后手段,不是第一反应。
- **污染会话的交接结论要重验**再采信。
- **改引擎/采集 SQL 的部署后必须手动重跑重算**,并核对产物(列非 NULL、
  行数、抽样值);重算窗口:日常 45 天,动了历年口径用 5000 天全量
  (约 20-40 分钟,anchor_row 是大头,nohup + 轮询)。
- **单人自用面板,极简发布**:备份 + 一键回退 + 本人验收,不搞灰度/多负责人。

- **同一个数字在两个页面对不上,先查两条取数路径的时序**(2026-08-18):
  高盛 08-17 掉榜,报告表算得出 2,334 手,净持仓页一片空白。两处都对——报告表
  走**读时**反推,净持仓页读**库里**的反推行,而写反推行的脚本挂在 collector
  里(16:00),官方席位却要等 16:25 的另一条链才入库。反推的依据是回榜日的
  增减量,拿不到回榜行就整段推不出来,官方源品种因此永远滞后一整轮
  (实证:大商所席位由 collector 自采,反推到 08-17;上期所郑商所停在 08-14)。
  **一条流水线上,写数据的步骤排在读数据的步骤后面,不会报错,只会静默地
  少算一轮。**加派生步骤时要问的是「它依赖的行,这一刻真的已经在库里了吗」。

- **测试 mock 缺字段不是「写简单点」,是让组件在渲染期读到 undefined**
  (2026-08-18):给净持仓页加了个读 `day.inferred_members.length` 的
  computed,mock 里没这个字段,于是三个 unhandled rejection——而
  **74 个断言全绿、`Test Files 13 passed`,只有进程退出码是 1**。
  按接口补齐 mock,不要在生产代码里加 `?? []` 去迁就 mock:那是拿真实路径的
  防御性代码掩盖测试数据的缺陷。收工看的是退出码,不是那行绿字。

- **「加个功能」与「这个功能该长在哪」是两件事**(2026-08-18,运营者两次纠正
  同一个页面):净持仓要的是多席位合计 + 收藏,我做成了**独立页面**,还特意把
  两边的选择做成各记各的。功能一件不缺,但在席位持仓选好一家、点过去还得再选
  一次——运营者说的「没有联动」。**新功能默认长在已有界面上,另起一个页面要有
  明确理由**;当两个界面共享同一组输入(这里是席位与交易日),它们就是一个页面的
  两个子页,不是两个页面。

- **部署卡在「Deploy, migrate, and run VPS acceptance」不代表没部署成功**

  节奏下亮得起来"**(本次落成 `test_不许把判据窗口收成锚点`)。
- **「和回测对齐」要先问清对齐的是哪个维度 —— 常常不是数字,是对象**(2026-09-03,
  DEC-189)。压力判据看「主力剩 ≤30 日」,回测看「近月剩 ≤20 日」,我第一反应是把
  30 收成 20。错了:主力在剩 20 日之前就换月,收窄等于把 ⚡ 关掉。研究量的一直是
  **换月之后那个正被赶出场的近月**,而生产在看**主力** —— 差的不是十个交易日,
  是合约的角色。**把两边的口径并排写成一句话再动手**:「谁、在它人生的哪一段、
  用哪一天的数」,三个都对上才叫对齐。
- **拿当前值去比历史分布时,「哪一天取的」和「取的是谁」一样重要**(同上)。
  对齐对象之后还差一步:当前值原来取在**今天**,历届分位取在**锚点日**。
  散户剩仓随交割临近单调走低,于是当前值系统性偏大(16 届中位 +1,556 手、比值 1.20),
  天然容易亮。改成也读锚点日那一格之后两把尺子才一样长 —— 而且它**顺带把
  「每届一次」实现了**:整段窗口读同一个数,不会因为剩仓抖一下就忽明忽灭,
  不需要另外存状态。**能靠取数口径实现的状态,不要用状态机去实现。**
- **回放脚本只截断一半输入,得出的结论会指向错误的合约**(同上)。核对新口径时
  我把 `mkt`/`seat` 按日期截断了,`st`/`vols` 没截 —— `vols[c].tail(20)` 于是取到
  **今天附近**的量能,次主力那一腿被挑成未来才放量的合约(LH2605 的对手腿印成
  LH2611,真值 LH2607)。判据本身没受影响,但我差点据此报一个不存在的缺陷。
  **回放的输入必须整份按同一个日期截断,少截一个都算前视。**
- **一段只有部分品种才走到的文案,改完要把每个分支都跑一遍**(同上)。给 note 加了
  第二个 `%d` 而末尾仍是 `% anchor` 一个参数 —— `TypeError`,但那段话只有判据级
  品种才走到,拿展示级品种冒烟看不出来,是全量测试才炸的。
- **规则改动的验收标准是「逐届与报告对得上」,不是「测试变绿」**(同上)。
  这次的判据在生产数据上重放出生猪 7 届胜 86%、鸡蛋 11 届(6 空 5 多)胜 82%,
  **触发的届与两份报告里的明细逐个相同** —— 这才是「对齐了」的证据。
  单元测试只能证明代码按我写的那样跑,证不了它跑的是回测那条规则。
- **带符号的数,页面上必须把符号翻译成方向词**(2026-09-03,运营者当场指出
  「这净剩仓 7,686 手,多单还是空单,写清楚」)。散户净剩仓是「多单 − 空单」,
  正数净多、负数净空,而**方向就是信号本身**:净多剩仓压近月(⚡做空价差)、
  净空剩仓托近月(⚡做多价差,镜像分支)。原来只印 `toLocaleString` ——
  正数看不出是多,负数只有一个不起眼的减号,历届四分位「1,164~8,419」更是
  让人默认都是净多(鸡蛋历届里有 −23,929 的届)。**PITFALLS 里早有「交易信号
  必须把方向写在标上」(DEC-088),这次是同一条纪律在「一个数」上又漏了一遍** ——
  凡是可正可负、而正负各有业务含义的量,渲染层一律走一个带方向的格式化函数,
  不许直接 `toLocaleString`。
- **写着「凡是数字都从实参算,不许写死」的那个函数,第一句话自己是写死的**
  (2026-09-03,DEC-190 顺手查出)。`_caveats` 给**每一个品种**发同一句
  「样本只有三年(2023-08 起,大商所席位数据起点),且只有一种市况——全程熊市」。
  对生猪/鸡蛋/焦煤成立,对另外三个全错:玻璃是郑商所、13.7 年样本(**同一屏的
  risk_flags 自己写着「13 年里有 4 年是亏的」**),纯碱 6.3 年,而且这三个品种同期
  「恒定满仓做空」都是**亏**的 —— 也就是价格整体在涨,「全程熊市」正好说反。
  **一个函数的 docstring 挡不住它自己第一行的违规**;查这类问题的最省事办法是
  **把同一屏上两处对同一件事的说法摆在一起对**(13 年 vs 三年,一眼就穿帮)。
- **「后半样本衰减」先别当成「最近失效」,把切点落在哪几年看清楚**(2026-09-03,DEC-190)。
  纯碱前半夏普 1.08 → 后半 −0.16,读起来像规则正在坏掉;逐年一拆,后半罩住的正是
  DEC-113 上线时**就写明会让利**的 2023/2024,而**最近两年成本臂反而跑赢**被它替换掉的
  旧信号。三种切法的差异 t 全在 ±2 内。**等分样本的切点是任意的,它不认识你的
  决策记录**;凡是拿前后半下结论,先问一句「切点两边各是哪几年,那几年发生过什么」。
- **规则「没变差」和规则「还在开门」是两件事**(同上)。纯碱进场笔数从 22 笔/年
  塌到 4 笔(2025)、6 笔(2026),根因不是判据变钝,是它拿来比大小的两个水平量
  **不再协整**:「价格−成本」自 2023 年起单向走到 −2~−3% 并停在那里,为正的天数
  从 62% 掉到 20%,门就常年关着。**收益率指标看不见这件事**(少数几笔还可能是正的),
  要盯的是**触发频率**。对照组很关键:鸡蛋同一指标 2025 也漂过一年、2026 回来了 ——
  那才是协整该有的样子。
