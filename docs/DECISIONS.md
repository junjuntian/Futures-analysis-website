## 3. Workspace 与租户隔离

### `DEC-013` Workspace 数据归属

状态：已确认。

- 业务数据归属于 `Workspace`，不直接归属于 `User`。
- MVP 中每个用户自动对应一个个人 Workspace。
- MVP 不实现 Workspace 共享、成员邀请和跨用户协作。
- 所有业务表必须包含 `workspace_id`，查询、唯一约束、审计、任务、对象存储和 AI 工具均以 `workspace_id` 作为强制隔离条件。
- `users`、认证 session 和系统级角色属于身份基础设施，不以 `workspace_id` 作为业务归属。
- 不允许由客户端自由指定可访问的 `workspace_id`；服务端从已认证 session 解析当前 Workspace。
- 系统管理员身份不自动授予跨 Workspace 业务数据读取权限。

影响：产品权限、数据库模型、API 查询、后台任务、文件对象、浏览器会话、AI 工具和验收标准。

## 4. 分析范围和时间口径

### `DEC-014` MVP 排除历史回测

状态：已确认。

- MVP 不实现规则驱动的历史回测、自动生成交易信号或模拟成交。
- MVP 只提供历史统计、季节性、百分位、极值、回撤和情景计算。
- 真实成交的胜率和盈亏统计不属于回测，但只能基于完整 `trade_group`。

### `DEC-015` 时间、交易日和交易日历

状态：已确认。

- 系统时间点统一以 UTC 和 PostgreSQL `timestamptz` 保存。
- 业务展示和默认业务时区为 `Asia/Shanghai`。
- 市场数据独立保存 `trade_date` 和 `session_type`。
- 夜盘按照对应交易所的交易日历归入下一交易日。
- 交易日历按交易所分别维护，具有版本号，并支持带审计的人工修正。
- 任何按日统计都必须记录所使用的交易日历版本。

## 5. 价格、合约和交易口径

### `DEC-016` 价格口径

状态：已确认。

- 收盘价 `close_price` 与结算价 `settlement_price` 分别保存。
- 行情图默认使用收盘价。
- 日终持仓、未实现盈亏和权益默认使用结算价。
- 已实现盈亏使用实际成交价。
- 价差、统计、图表、持仓和报告结果必须记录 `price_basis`。

### `DEC-017` 连续合约与换月

状态：已确认。

- MVP 不自动生成连续合约。
- 允许导入外部连续合约数据，但必须记录数据来源和换月规则。
- 后续内部换月规则必须版本化，并单独记录换月事件。
- 外部连续合约不得与实际交割合约数据混用或伪装成原始合约行情。

### `DEC-018` 成交、配对和盈亏

状态：已确认。

- 原始 `trade_fill` 不允许覆盖修改；纠错使用冲销/补偿记录并保留关联。
- 开平配对默认采用 FIFO。
- 加权平均仅用于展示当前持仓成本，不用于改写成交配对或已实现盈亏。
- 已实现净盈亏包含手续费。
- 胜率按已完成的完整 `trade_group` 计算，不按单笔成交计算。

## 6. 标识和数值类型

### `DEC-019` 主键策略

状态：已确认。

- 普通业务实体使用应用层生成的 UUIDv7。
- 高频时间序列和明细表使用 PostgreSQL `BIGINT GENERATED BY DEFAULT AS IDENTITY`。
- 使用 BIGINT 的表必须通过业务字段建立包含 `workspace_id` 的唯一约束。
- 对外 API 不得依赖 BIGINT 的连续性表达业务顺序或数量。

### `DEC-020` 金融数值精度和币种

状态：已确认。

| 语义 | PostgreSQL 类型 |
| --- | --- |
| `price`、`spread` | `numeric(20,8)` |
| `money`、`fee`、`pnl` | `numeric(24,4)` |
| `ratio` | `numeric(20,10)` |
| `lots` | `bigint` |

- 金融数据不得使用浮点数作为数据库最终存储类型。
- 数据库模型支持 `currency_code`，默认 `CNY`。
- MVP 界面仅开放人民币，不实现汇率换算。
- Rust 领域和数据库边界使用十进制定点类型；浮点数只允许用于明确误差范围的临时统计计算。

## 8. 凭据和浏览器安全

### `DEC-022` 信封加密和主密钥

状态：已确认。

- 敏感数据使用信封加密：数据由 DEK 加密，DEK 由版本化主密钥/KEK 包裹。
- 主密钥不得存入数据库、代码仓库或 Docker 镜像。
- 密文记录保存加密算法、`wrapped_dek` 和 `kek_version`，不保存主密钥本身。
- 主密钥轮换通过重新包裹 DEK 完成，不要求解密并重写全部业务明文。
- 数据库备份与主密钥恢复副本必须分开保存。

### `DEC-023` 远程人工登录

状态：已废止（由 `DEC-031` 替代，2026-08-02）。

以下为原决策内容，仅为变更审计保留，不再生效：

- 远程登录使用隔离 Chromium 容器、Playwright 和 noVNC。
- 每个 Workspace 与数据源组合使用独立 Browser Context。
- noVNC 会话必须短期授权、不可直接公开暴露，并与应用 session 绑定。
- 登录状态使用信封加密保存，不得写入 Git、普通日志或未加密对象。
- 采集浏览器与图表渲染浏览器必须保持独立信任边界。

## 10. Phase 1 补充决策

### `DEC-026` 首次用户初始化

状态：已确认。

- 系统中不存在用户时，允许访问一次性初始化接口或初始化页面。
- 初始化必须校验一次性 bootstrap token。生产与 VPS 环境使用 `BOOTSTRAP_TOKEN_FILE` 指向只读挂载文件，当前 futures VPS 约定宿主路径为 `/etc/futures-platform/secrets/bootstrap-token`，`root:root` 且权限 `0400`；不得写入 Git、数据库、镜像、日志或普通 `.env`。开发环境可使用等价临时文件；环境变量 `BOOTSTRAP_TOKEN` 仅允许非生产本地调试。
- 初始化在单个数据库事务中创建首个管理员用户、个人 Workspace 和 Workspace Owner 成员关系。
- 初始化不自动创建虚构交易账户。
- 首个用户创建成功后，初始化入口永久关闭，并立即使 token 失效；文件来源的 token 必须删除。
- 并发初始化只能有一个请求成功，必须通过集成测试验证。

### `DEC-029` futures VPS 主密钥托管

- 数据库只保存 `wrapped_dek`、`kek_version`、`nonce` 和算法信息。
- 支持主密钥版本轮换；离线恢复副本与数据库备份分开保存。
- 部署文档必须写明恢复和轮换步骤，且不得泄漏明文密钥。

## 11. Agent 工作流与上下文交接

### `DEC-036` Planner/Generator/Evaluator 工作流

状态：已确认。

- 主 Agent 负责编排，固定使用 Planner、Generator、Evaluator 三个角色。
- 工作流为：Planner 制定计划 → 文档审查 → Planner 修正文档 → Generator 实现 → Evaluator 审查 → Generator 修复 → Evaluator 复核 → 全部验证通过 → Git 提交。
- Planner 不写业务实现代码；Generator 不改变已确认业务口径；Evaluator 原则上只读并输出证据化审查。

### `DEC-037` 上下文轮换与交接

状态：已确认。

- 上下文接近上限、阶段完成、日志/代码积累过多、用户要求换新 AI 或 AI 无法可靠记住前序决策时，必须执行交接。
- 交接文档使用不可覆盖路径 `docs/handoffs/HANDOFF_YYYYMMDD_HHMM.md`。
- `docs/handoffs/LATEST.md` 只指向并概括最新交接状态，不删除历史文件。
- 交接必须记录 Git、未提交修改、任务状态、决策、测试、VPS、迁移、服务和下一步第一条操作。
- 交接文档不得包含密码、API Key、Cookie、Token、主密钥、数据库明文凭据或其他秘密。
- 新 AI 必须通过 Git、测试和运行环境核验交接内容，不得盲目信任摘要。

## 12. 总方案重审决策

### `DEC-038` 自动采集免确认

状态：已确认。

- 白名单数据源的结构化自动采集数据免人工确认、免提取预览，直接进入正式表。
- 兜底机制：解析或校验失败的批次自动隔离为 `failed`，不写正式表；批次可整批回滚；数据质量警告仅记录、不拦截。
- 人工确认仅保留于手动文件导入的既有流程，该流程不变。

### `DEC-039` 采集范围与历史回填

状态：已确认。

- 范围：全市场日行情（收盘价与结算价）、全市场席位龙虎榜（各合约成交量、持买、持卖排名）、交易日历、合约参数。
- 历史回填全部可得历史。
- 执行策略：行情全量一次拉取；席位倒序分层，先近 5 年，再由后台任务向更早年份补拉；不可得年份留记录、不阻塞。
- 磁盘达到 80% 水位时扩容 VPS 磁盘，不更换机器。

### `DEC-040` 图表导出

状态：已确认。

#### 部署两次回滚的根因（2026-08-10 查实）

`5bc0e6b` 给价差历史加了保留量限制（删旧数据），**授权没有跟上**。API 实际以
`futures_runtime` 连库，该角色在这几张表上只有 select/insert（缓存表多一个 update），
没有 delete：

- 清缓存 → 每次上游取数都记 `permission denied for table spread_provider_cache`
- 限制已存序列的保留量 → 在**刚写完该序列的同一个事务里**失败，就是
  `free-spread/query`（焦煤 09-01）那个 500，连续两次部署因它回滚

`spread_provider_observations` 与 `spread_window_segments` 由 `on delete cascade`
牵连——级联删除同样是对被引用表的删除，同样需要该表的权限，只授权父表会把同一个
错误往下推一张表。

修复：迁移 `202608100005` 补齐四张表的 delete 授权，并在迁移内断言授权确已生效
（静默无操作的迁移会原样留下它本该修掉的故障）。

**为什么拖了这么久**：`futures_app` 是超级用户，任何权限检查都通过，所以"没写的授权"
和"写了的授权"在它身上看起来完全一样。之前我确实猜过 DELETE 权限，但拿它去验，
于是排除掉了正确答案。证据其实一直在部署失败时抓取的 `failure-service-logs.txt` 里，
写着 `permission denied`——**我之前没去看那个文件**。

已加静态测试 `every_table_this_module_deletes_from_is_granted_delete_to_the_runtime_role`：
代码里 `delete from spread_*` 的每一张表，都必须在迁移里对 `futures_runtime` 有 delete
授权，否则测试失败。

#### `price_multiplier` 种子没落库的根因（2026-08-10 查实）

`202608100003` 加了列、断言"种子已落库"、迁移记录在册、部署成功——**但八个品种全是 NULL**。

根因是我在那条迁移的注释里写了一句**没有核实的话**：「migration role has BYPASSRLS」。
实际 `futures_migrator` 的 `rolsuper=f, rolbypassrls=f`，而 `instruments` 开着
FORCE RLS，策略是 `workspace_id = app.current_workspace_id()`。迁移没设工作区上下文，
于是 UPDATE 匹配 0 行。

**更要命的是那条断言本身也瞎了**：它 `select count(*)` 读的是同一张被 RLS 挡住的表，
数出 present=0、seeded=0，两者相等，于是通过。**读不到自己要断言的行的断言，不是断言。**

修复 `202608100006`：照 `202608030002` 已有的写法按工作区循环 `set_config` 设上下文再写。

**断言改成校验机制而不是数据量**：设完上下文立刻断言
`app.current_workspace_id() = 目标工作区`——当初坏的正是这一环。
（第一版我写成"跨所有工作区一个都没种到就报错"，被 CI 打回：全新空库本来就没有
instruments，那不是故障。数据量做不了判据，机制可以。）
另加一条：鸡蛋必须是 10（不是 5 吨的合约单位），在循环内逐工作区检查。

**教训与 DELETE 权限那次完全同类**：对角色权限的假设不核实就写进注释，然后照着假设
设计校验。两次都是这样。

#### 开高低量额一直没落库（2026-08-10 单日验收时发现）

`19b5d97` 加了迁移（`market_prices` 的 open/high/low 三列）、也让采集器开始输出
开高低量额，**但写库的那一步没改**。列建好了、数据也送到了，投影只写 close 和
settlement，其余静默丢弃。导入全程报成功。

实测：全库 14,429 行，**0 行有开盘价**；`volume` / `turnover` 连列都没有。
这直接砍掉两件事——建仓过程的 K 线图就是这个区间，`price_multiplier` 的交叉校验
（成交额 ÷（成交量 × 结算价））也依赖它。

**这条链路一共断了四处**（第一次修完再验，才发现前面还断着）：

| 环节 | 状态 |
| --- | --- |
| 迁移建列（开/高/低） | 做了 |
| 采集器输出五个字段 | 做了 |
| **领域层 `MARKET_DATASET_FIELDS` 声明** | **没做——真正的闸门，CSV 送到了在入口被按模板丢弃** |
| **投影写库** | 没做 |
| 量/额的列 | 根本没有 |

修复：
- `rust/crates/domain/src/import.rs` 的 `MARKET_DATASET_FIELDS` 补上
  开盘价/最高价/最低价/成交量/成交额
- `202608100007` 给 `market_prices` 加 `volume` / `turnover` 两列（numeric，
  十三年成交额求和会溢出 bigint）
- 投影的 insert 与 update 两条路径都补上开、高、低、量、额
- 测试 `the_market_projection_writes_every_value_column_the_table_carries`：
  投影的 insert 必须写、update 必须刷新每一个价格类列，少一个就红
- 测试 `test_the_collector_and_the_platform_agree_on_every_column`：**跨语言契约**，
  采集器 `DATASET_FIELDS` 与领域层 `*_DATASET_FIELDS` 必须逐字段双向相等。
  两边分处两种语言两个 crate，此前没有任何东西把它们连起来，这就是字段被静默
  丢弃的根本原因

**这是今天第三次同类问题**：改动只做了一半（迁移建了列 / 注释假设了权限 /
断言读的是被挡住的表），而"部署成功"和"导入成功"都不会告诉你少了什么。
真正发现它的是拿一天的数据去和交易所原文件逐字段对。

#### 一条被推翻的中间结论（留档）

一度判定「`requests` 把逗号编码成 `%2C` 导致 K 线接口断连」。**该结论错误**：
以 2 秒间隔交替 A/B 三轮，`%2C` 成功 2/3、字面逗号成功 3/3——端点两种都接受，
失败源自节流。当初的三次 `%2C` 失败是背靠背发出的，与限速混淆了。
代码里仍以字面逗号发送，理由只是「与上游自己的请求形状一致」，不是修复。

### `DEC-048` 掉榜持仓自行反推，大商所以三禾在榜日的增减为基

状态：已确认（2026-08-12，实证后由用户拍板）。

- 交易所只公布每个榜的前 20 名。会员掉出榜单的那天官方文件里没有他这一行，
  **那是“不知道”，不是“零”**。数据层、成本引擎、页面三处一律以 NULL 表达未知，
  口径见 `docs/SEAT_AND_SPREAD_REQUIREMENTS.md` 第 4A 节。
- 掉榜前一日可以反推且只能反推一天：`昨日真实持仓 = 今日持仓 − 今日增减`。
  该恒等式在官方数据 267,373 个相邻交易日样本上 100.000% 成立、零例外。
  推不出来的日子**不写行**。
- **大商所以三禾在榜日的增减为基。** 大商所没有官方那条路（`DEC-041`，WAF 全局拦截），
  三禾是唯一有历史的源。原先一律排除三禾，理由是它的增减是“清零差分”；实测表明
  那只出现在它自己回写过的行上，指纹为 `增减 = −前一行持仓`，可精确识别：
  33.3 万个相邻交易日样本中，恒等式成立 327,675、带指纹且失败 5,317、无指纹且失败 9。
  排除指纹行后复现率 99.997%，与官方源同一水准；而真正要用的“回榜行”那一侧
  10,722 个样本中零指纹。
- 带指纹的行由 `fix-sanhe-fabricated-changes.sql` 修成真实增减
  （真实增减 = 今日持仓 − 昨日持仓，两值均在库且已印证，是算术不是造数）；
  持仓仍为 0 的由 `fix-sanhe-fabricated-zeros.sql` 处理。两者都在日更管线里，
  因为三禾每天仍按同样手法写入新行。
- 反推行标 `source='reboard_inferred'`，名次与增减留空，且不进品种汇总——一份
  “有时含反推、有时不含”的合计会凭空造出 ΔNet 跳变，对趋势跟随比稳定地少算更糟。

影响与优先级：本决策取代 `DEC-042` 中“席位接口不在授权范围”所隐含的“大商所席位
只能靠三禾直采”的做法。缺口由自建反推补齐，覆盖全部会员而非八家，且推不出来的

### `DEC-053` 席位成本统一为逐合约口径，并以对拍守卫防双实现分叉

状态：已确认（2026-08-14）。

- **背景。** 「机构成本」这一个概念有两份独立实现：Rust
  `domain/src/seat_cost.rs`（面板建仓过程）与 Python `engine/smart_money.py`
  （信号引擎的买入区间）。2026-08-14 发现两者长期不一致：东证 2026-07-15 引擎
  算出 960.40，而它两个实际合约都在 900 附近。
- **根因。** 引擎那版按**品种汇总**推成本、用主力合约结算价；移仓时（平旧约 +
  开新约）只看到净仓大幅波动，而算法是「加仓按结算价加权、减仓不改均价」，
  加仓腿把成本拉高、减仓腿不修正，反复移仓后系统性偏离。
- **决定。** 引擎改为逐合约推算再加权合并，与 Rust 对齐。另有三处按 Rust 语义
  修正：掉榜日冻结全部状态（不补零）、加仓量取净持仓绝对值增量（不用交易所
  公布的 change）、建仓当日无结算价则成本永久不可知（不硬算）。
- **加守卫。** `ops/cost-parity-check.py` 直接调引擎的 `seat_cost` 与 Rust 端点
  对拍，容差 0.01 元，样本不足 50 组即判失败；已接入 `phase_5a_e2e.sh`，
  每次部署自动跑。**守卫自己不实现算法**——首版就是自己抄了第三份，结果引擎
  修好后守卫仍报同样的分歧。
- **两处有意保留的差异**（守卫已避开，不是 bug）：引擎只记多头成本（买点不该
  由净空席位参与）；`reboard_inferred` 反推行 Rust 保留而引擎的 `clean_seat`
  一律剔除（`DEC-048` 的既定口径）。
- 本项目已在「同一概念多处实现」上栽过两次，第一次是 v51 权重快照与生产引擎
  漂移。见 `research/PITFALLS.md` 第 9 条。

### `DEC-054` 合约汇总按各合约净方向分两腿，取数用逐合约榜

状态：已确认（2026-08-15，由用户细化）。口径全文见
`docs/SEAT_AND_SPREAD_REQUIREMENTS.md` 2.3 节。

- **决定。** 建仓过程的合约汇总档，把该席位在各合约的持仓**逐一算完成本再合并**，

  **这一段写在页面上，不藏着。**
- **顺带修掉两个取数缺陷**：①汇总档此前取不到任何结算价（行情被 `contract`
  限死），成本/当日盈亏/累计盈亏三张图全是空的；②取数没过滤 `rank_type`，
  某席位某天只上成交量榜时被算成「多空双零」即平仓，成本清零并算出一次不存在

### `DEC-062` 套利监控:加「新触发」标记与「历史回归率」,并改掉暗示回归的读法

状态:已确认(2026-08-17,用户看完极值事件研究后指示落地这两项)。

- **来历。** 用户提出「今年鸡蛋和焦煤都是历史级别的价差,3% 触发时有多少套利
  席位进场」。按监控脚本的口径重算了全部历史(监控表本身只回算到 2026-04-14),
  做事件研究,得到三条与页面现有读法直接冲突的结论:
  1. **极值处并没有套利资金涌入。** 触发日席位的同步反向建仓活跃度只有平常日的
     1.14~1.16 倍(2026 年口径),已确认的套利席位只占进场量的 21~24%。
  2. **价差在极值处不回归。** 段首日起 20 个交易日,按「该回归的方向」计:鸡蛋
     445 段里 200 段(45%)朝回归走、均值 −22 点;焦煤 68 段里只有 20 段
     (**29%**)、均值 −19 点。这条只用价格数据,不依赖任何席位假设。
  3. **阈值在单边突破的行情里失去筛选力。** 焦煤 2026 年有 **64.2%** 的交易日都在
     3% 触发——价差持续创新低,滚动区间天天被刷新;而连续触发段的中位长度只有
     3 日(鸡蛋 2 日),说明绝大多数段很短,长段拖着不放才是噪音来源。

- **决策一:段首日标记(`is_new_alert`)。** 表里存**前一交易日的两轨位置**
  (`prev_pair_position` / `prev_years_position`),不存「是不是段首日」。读时对
  前一日套同一个阈值,前一日不触发而今天触发即为新触发。这样任何阈值都能在任何
  一天重判,历史跟着一起变——与 `DEC-047`(监控只存位置不存触发结论)同一条原则。
  界面加「仅新触发」筛选与「新」徽标。
  - 前一日位置整个缺失(该组合第一天、或前一日无快照)时**不打标记**:判不了就
    不标,宁可漏标也不假报。这一条单独有测试钉住——把「不知道」当成「刚触发」,
    页面上会天天冒出假的新触发,而且看不出是假的。

- **决策二:历史回归率(`revert`)。** 每行冗余存该**月份组合模板**的命中数与样本
  数,3% / 5% / 10% 三档 × 低/高两侧共 12 列。口径与取舍:
  - **主体是模板不是具体合约对**(同品种 + 同月份对 + 同年差,如鸡蛋 09-01)。
    JD2609/JD2701 一辈子只有一个生命周期,极值段两三段,算不出有意义的比率。
  - **极值段按当年轨划分**,不用页面报警的合成轨。合成轨要先有历年百分位,而历年
    轨是逐 (组合,日期) 跑一次 `percentile_cont` 算的,推到全历史会从百来次变成
    几万次。**这是工程折中,不是口径上更优**——因此页面必须标注口径,并说明与报警
    口径可能有出入。
  - **段首日起 20 个交易日**看方向。不足 20 日的段自然不计入,统计因此永远落后
    20 个交易日,这是对的:那些段的结果还没发生。
  - **存整数计数而不是比率**:界面上「52 段里 28 段」比孤零零一个 54% 更能让人看
    出样本有多薄;样本为 0 存 NULL 而不是 0,`0/0` 显示成「0% 回归率」是最坏的
    一种错——看着像结论,其实是没有数据。
  - **三档而不是一档**:请求阈值是连续的,只存一档会出现「页面按 3% 报警、底下挂
    着 10% 的回归率」这种对不上的展示。读时取与当次阈值最接近的一档,并把档位原样
    回给界面标明。
  - **配色避开红绿**:回归率是个概率,不是价格方向。全站红涨绿跌是价格语义,借过来
    会被读成「红=看涨」,只用主色与灰色的深浅分强/中/弱。

- **决策三:文案改中性。** 页头加一段「贴到极值不等于会回归」,并把鸡蛋 45% /
  焦煤 29% 的对比直接写在上面。**这不是措辞问题**:按原读法用这个页面会亏钱。

- **上线后的实测**(2026-08-14 快照,43 组):同为低位触发,鸡蛋 JD2611/JD2612 的
  历史回归率是 45/54 = **83%**,JD2609/JD2702 只有 15/37 = **41%**;焦煤
  JM2701/JM2705 高位 21/75 = **28%**。组合之间差一倍以上,而页面此前把它们画成
  同一个红条——这就是加这个字段的全部理由。

- **⚠️ 开发期事故留档。** 做「事务里跑一遍再 rollback」的只读验证时,拼接脚本的
  grep 转义没生效,compute 脚本自带的 `commit;` 没被剥掉,这套 DDL 与一次窗口内
  重算**当场落进了生产库**。后果可控(列可空无默认、当时的生产代码不读新列、日更
  不会失败),但它让迁移在正式部署时必然撞「列已存在」。已把 14 个加列改成
  `add column if not exists`、约束改成 `drop constraint if exists` + `add`,并加
  测试钉住。**规则:迁移必须能在已处于目标状态的库上再跑一遍而不报错**——同类
  教训仓库里已有一次(concurrently 预建索引的迁移),这是第二次。

- **⚠️ 修订(同日,决策二被推翻重做 → 迁移 202608170002)。** 运营者指出回归率算错了:
  「回归率应该按月份计算,比如 JD09 和 01,交易时间是 1.29-8.31…比如 6.1 日 741 报警了,
  后续回归概率要从历年的 6.1-8.31 进行计算…后续的任何一天收盘低于 741 都算回归」。

  1. **固定 20 个交易日与合约剩余寿命无关。** 鸡蛋 09 合约 8 月末就退出散户可交易
     区间,8 月中旬触发时只剩十来个交易日,拿 20 日后的价格去比,比的是已经不可
     交易的东西。
  2. **只看第 20 天那一个点。** 中途回落过又涨回去的按终点算是「没回归」,可套利仓
     在那期间随时能平掉。

  起点**。差距不是调参能补的,是口径错了。新口径:
  - **可交易窗口照 5A 窗口引擎**(`rust/crates/domain/src/spread_analytics.rs`),不另
    立一套:起点 = 两腿都有数据的第一天;止点 = **先到期**那条腿的散户最后交易日,
    即 `last_weekday_before_delivery`(交割月前月最后一个非周末日)。运营者明确要求
    「改成 5A 窗口那套规则」。
  - **历年按月-日对齐**,一直看到各自窗口止点;**曾经触及**即算回归,不比终点;只用
    **已走完**的年份实例;**不要求**历年该时点也处于极值(运营者定:绑上报警会把样本
    砍到三四年)。
  - **幅度用点数**(运营者定):价差跨零时百分比会爆——2019-08-14 起点 −8 点、回落
    407 点,百分比是 5000%。
  - **不设样本年数门槛**(运营者定):生猪 5 年、纯碱 6 年,设门槛整个品种就没统计了;

  - **存四个数而不是一个比率**,因为单看回归率会骗人:剩余期一长它就趋近 100%(苹果

### `DEC-063` 套利监控:分层通用规则上线(✓ 合格 + 已拐头)

| 决策范围 | 既有文档状态 | 冲突结论 | 已完成修正 |
| --- | --- | --- | --- |
| Workspace 归属 | 原设计把共享范围列为开放事项，部分表使用 `owner_user_id` | 有冲突 | 新增 `workspaces`；业务表、任务、对象和 AI 全部使用 `workspace_id` |
| 回测边界 | 原方案同时出现“按规则统计胜率”和“后续再做回测” | 有冲突 | MVP 只保留历史统计、情景计算和真实 `trade_group` 统计 |
| 时间与夜盘 | 原设计标记为待确认 | 无既定实现冲突，但存在缺失 | 固定 UTC、Asia/Shanghai、`trade_date`、`session_type` 和版本化日历 |
| 价格口径 | 原数据模型以单一 `price_type + price` 表达 | 有模型冲突 | 改为分别保存 `close_price`、`settlement_price`，派生结果使用 `price_basis` |
| 连续合约 | 原设计将自动连续与换月口径留空 | 无既定实现冲突，但范围不清 | MVP 禁止自动生成，只允许带来源和换月规则的外部数据 |
| 成交与盈亏 | 原设计把 FIFO/LIFO、费用和归组口径列为开放 | 无既定实现冲突，但缺少确定口径 | 固定原始成交不可覆盖、FIFO、净盈亏含手续费、胜率按完整组 |
| 主键与精度 | 原数据库文档明确为待确认 | 无既定实现冲突 | 固定 UUIDv7/BIGINT identity 和四类金融精度 |
| 批次回滚 | 原设计已倾向冲突时中止，但仍保留选择空间 | 轻微歧义 | 固定整批原子回滚、冲突零变更、无部分回滚、补偿批次纠错 |
| 敏感数据 | 原设计只有“加密 + key_version” | 有设计深度冲突 | 升级为 DEK/KEK 信封加密、重新包裹轮换和备份分离 |
| 远程登录 | 原设计明确未确定交互通道，后曾确认浏览器登录基础设施 | 2026-08-02 已裁剪 | 废止 `DEC-023`、`DEC-034`；整套登录浏览器基础设施移除，未来需要时另行立项 |
| URL 与连接器 | 原设计已反对通用任意 URL，但 API 边界不够强 | 2026-08-02 已修订 | `DEC-031` 固定五交易所 akshare 采集器；`DEC-041` 仅为 DCE 增加官方优先、如实标源的新浪 fallback，其余四家仍禁止二手源 |
| 提取优先级 | 原设计采用多级网页提取与 OCR | 2026-08-02 已修订 | `DEC-025` 固定 akshare 封装的交易所公开接口与公开文件，删除 OCR 级 |
| 首次初始化 | 原设计未定义首个管理员创建方式 | 缺失 | 固定 `BOOTSTRAP_TOKEN` 一次性初始化、单事务创建用户/Workspace/Owner |
| 反向代理 | 原文在 Nginx/Caddy 间未选 | 有待确认项 | 固定 Nginx，职责限定为静态资源、API 代理和 SSE 支持；noVNC 代理已废止 |
| RLS | 原文作为可选纵深防御 | 有待确认项 | 固定启用 Workspace 级 RLS，并要求 `SET LOCAL` 与显式 `workspace_id` 双层防护 |
| noVNC 参数 | 原文缺少 token、超时和并发口径，后由 `DEC-034` 补充 | 2026-08-02 已废止 | 不再建设 noVNC 会话；登录类数据源未来另行立项 |
| 自动采集确认 | 原设计统一要求提取预览与人工确认 | 有冲突 | `DEC-038` 固定白名单结构化自动采集免预览、免人工确认，并以失败隔离、回滚和质量警告兜底 |
| 采集范围与历史 | 原设计未固定全市场范围和回填顺序 | 缺失 | `DEC-039` 固定四类数据、全部可得历史、分层回填与 80% 磁盘扩容水位 |
| 图表导出 | 原设计使用服务端渲染沙箱 | 有冲突 | `DEC-040` 改为 ECharts 前端导出 PNG/SVG，并保留 SVG 安全清洗验收 |
| 三禾自由价差 | `DEC-024/031` 曾随登录基础设施一并移除三禾 | 2026-08-05 有限恢复 | `DEC-042` 仅授权三个无需登录的只读 POST 端点，由 Rust 代理、限频和缓存 |
| 三禾席位接口 | `DEC-042` 原文写“不在授权范围，留待 Phase 7 另议”，而 2026-08-12 实际已按用户指示采集 | 文档与实现矛盾，已修订 | `DEC-042` 据实记录当日授权与同日停采及其数据依据；缺口改由自建反推补齐，见 `DEC-048` |
| 掉榜日持仓 | 原文只定了“断开显示，不连线”（画法），没定数据怎么表示 | 实现按缺省补零，一路错到成本引擎 | `DEC-048` 固定“缺席 = 未知 ≠ 零”，三层一律 NULL；反推只推一天，推不出来不写行 |
| AI 部署边界 | 原文存在 AI 能力设想但 Phase 1 边界不清 | 范围风险 | 固定 Phase 1 不实现 AI，后续统一 Provider、只读工具、SSE 和来源审计 |
| 导入通道 | 原设计为「人工上传 + 预览确认 + 批次回滚」，自动采集也走同一条路 | 服务的功能已取消，成本与收益倒挂 | `DEC-049` 整体摘除，日更改走直灌；`DEC-021` 随之废止 |
| 灾备形态 | 迁新机时以「老机仍在、随时可切」为退路 | 老机已删除，该退路不复存在 | `DEC-050` 固定退路为每日异地 dump + 部署链回滚，**无热备机器** |
| 机构成本 | 面板与引擎各有一份实现，无人保证一致 | 已实证长期分叉（东证 960.40 vs 900） | `DEC-053` 统一逐合约口径，并以对拍守卫接入部署验收 |
| 合约汇总 | 2.3 节只说「各合约加总、金额累计÷总手数」，未定方向 | 分不出多空两腿，且取数取不到结算价 | `DEC-054` 固定按各合约净方向分两腿，取数改走逐合约榜 |
| 首进场区间条件 | 曾于 08-15 加入「60 日区间下 70%」四条件 | 回测全程为噪音（±3pt，一两笔重定时） | `DEC-055` 当日采纳、次日撤销，全程留档 |
| 重挫买点基准 | 首版用 250 日滚动高点、次版用人民币本轮高点 | 固定窗口把 1246 后一整年标成重挫；人民币被汇率扭曲（2021 标出 69 个假重挫日） | `DEC-056` 终稿=伦敦金美元价 ±10% 分轮，运营者两次纠正均被数据证实 |
| 席位组扩充 | 海选曾提议中金进组、年轻席位 t=5 级频现 | 中金 2023 后零事件=哑火；年轻高 t=选择偏差标准形状；国贸/中泰现持仓为逆势小空单 | `DEC-057` 七家为现有数据与标准下的尽头，国贸/中泰永久排除，新增「当前持仓照妖镜」维度 |
| 极值的含义 | 监控页把「贴到历史极值」直接呈现为机会，页面读法暗示回归 | 事件研究实证：鸡蛋极值段仅 45%、焦煤仅 29% 朝回归方向走，按原读法用会亏钱 | `DEC-062` 每组标注自己的历史回归率并写明口径，页头改中性文案 |
| 触发的粒度 | 只有「触发/不触发」两态，长段与新进入极值不分 | 焦煤 2026 年 64.2% 的交易日都在 3% 触发，一片红等于没报 | `DEC-062` 存前一交易日位置、读时判段首日，界面加「新」徽标与「仅新触发」筛选 |
