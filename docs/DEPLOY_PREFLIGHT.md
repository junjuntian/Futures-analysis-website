# 部署前置条件

**每次部署前先跑 `ops/preflight-deploy.sh`，全绿再看本文剩下的部分。**

脚本能机械查的都在脚本里，不重复。本文只写脚本查不了、必须自己过一遍的东西，以及
每条规则背后是哪次失败教出来的——删任何一条之前，先想清楚那次失败会不会回来。

规则来源：2026-08-10 那天连续三次部署失败。三次漏的都是"我以为我记得"的东西。

---

## 一、脚本已经挡住的（跑一下就行，不用记）

| 检查 | 被哪次失败教出来 |
| --- | --- |
| 工作区干净、HEAD 已推送且等于 `origin/分支` | 建完镜像又推了文档提交，部署被 `acceptance_sha` 守卫拒绝 |
| 每条迁移写了 `schema_versions`、版本号与文件名一致、带 `begin;` | 部署在打包步报 `migration_missing_version_record` |
| 每条迁移列进了 `deploy-futures.yml` 的显式清单 | 漏列 = 代码上线而 schema 没到（leg-order 那次每个查询回 500） |
| `deploy/collector/` 下每个文件都装进了发布包 | `project-history.sql` 没装进去，线上只打一行 `PROJECTION_SKIPPED` 然后每天安静地不投影 |
| CI 在该提交上通过 | — |
| 四个镜像都发布了 | 重启 runner 杀掉了正在跑的 `Publish api`，整体仍显示 success，但少一个镜像 |
| runner 在线且空闲 | 同上：重启 runner 会杀掉它正在跑的作业 |

## 二、脚本查不了，必须自己过

### 1. 从建镜像到部署完成，不要推任何提交

推了 HEAD 就变了，部署被 `acceptance_sha` 守卫拒绝，**整套镜像得重建**（约 25 分钟）。
文档提交也算——那次挡住我的就是一个只改了 `docs/DECISIONS.md` 的提交。

要改文档就等部署完再改。

### 2. 改了写路径，就要走一遍真实的写

生产验收（`phase_5a_e2e.sh`）会真的建一条收藏、发一次查询。改动只要碰到写库的路
径，单元测试绿不等于它能写进去：

- 占位符跳号会让 uuid 列收到文本，**每次建收藏都 500**，而静态测试完全看不见。
  （现在有 `every_insert_numbers_its_placeholders_in_order` 盯着，但它只查编号顺序，
  查不了绑的值对不对。）

判断标准：**这次改动会不会让某个 `insert`/`update` 的列或绑定发生变化？**会的话，
要么本地连库跑一次，要么明确接受"生产验收会告诉我"。

### 3. 改了入口校验或加了新的取值，从入口验起

自研价差那次：引擎在生产数据上算出 2201 个点没问题，但 `validate_query` 在分支之前
硬比 `provider != "sanhe"`，请求根本进不了门。我写的四个测试全是直接调
`own_engine_legs`——**测了引擎，没测请求能不能进得来**。

判断标准：**新加的取值要经过几道校验？**每一道都要有测试从入口喂进去，而不是从中间
函数开始。

### 4. 动数据管线的 SQL，先在生产库做回滚式预演

在一个最后 `rollback` 的事务里，把迁移的实质部分和新 SQL 都跑一遍，看结果合不合理。
`project-history.sql` 那次预演挖出两个**上线后不报任何错**的问题：

- 郑商所合约在 `contracts` 里是三位月份（`AP701`），四位正则一过滤，263 个合约一个
  不剩——玻璃、苹果、纯碱从此不再更新，日志干干净净。
- akshare 给郑商所和上期所的成交额是**万元**，而 `price_history` 这列定义是元。同一
  列两种量纲，会让"成交额 ÷（成交量 × 结算价）= 点值"这条自证校验彻底失效。

判断标准：**这段 SQL 有没有过滤条件或单位换算？**有的话预演一次，看落进去的行数和
数值本身，不只看它没报错。

### 5. 部署完要验到端点层，不能只验前端包

自研价差那次我查了前端包里 `provider:"self"` 有两处、`sanhe` 零处，就下结论"切干净
了"。**验证了前端确实在发 self，没验证后端收不收 self。**

部署后至少确认：

- 三个镜像 digest 与构建产物逐个对上
- 新迁移出现在 `schema_versions`
- **构造一个真实请求打到新端点**，看它返回什么——不是看路由存在（401 只说明路由在）

## 三、部署失败后

- 生产没被改动：验收失败会拦下发布，线上仍是上一版。先确认这一点再动手。
- 失败原因看 `gh run view <id> --log-failed`；真正的失败步骤往往在报错那步的**上面**，
  后面的报错常常只是收尾步骤的连带（比如 SSH 密钥已被清理）。
- 修完要从建镜像重来，因为 HEAD 变了。

## 四、别做的事

- **不要在作业运行时重启自建 runner**，会把作业杀掉。runner 卡在队列里不领活时才
  重启，重启前先确认 `busy=false`。
- **不要为了让部署过去而放宽守卫**。那些守卫每一条都是被一次真实事故加上的。
